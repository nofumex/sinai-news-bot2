# Точечное исправление /start и примечаний · 12.10.2026

Архитектура, SQLite, очереди и polling сохранены. Изменения касаются выбора кнопок при /start, повторной постановки привязки в очередь, восстановления и обновления примечания подписки.

## Найденные причины

1. `/start` безусловно передавал `group_buttons()` в отправку: группа пользователя не проверялась.
2. Повторный выбор группы использовал только `INSERT OR IGNORE`: ранее неуспешная задача привязки с тем же ключом оставалась неуспешной. Обработчик привязки уже связанного пользователя сразу завершался, не восстанавливая задачу примечания. Для `notes.status=done` код не проверял CRM и не обновлял текст. Примечания не пересчитывались после изменения группы, периода или следующей отправки.
3. При проверке этого каталога рабочей БД ещё не существовало, запущенный локальный Python-процесс не найден, Telegram возвращал 0 ожидающих обновлений. Поэтому локально не было данных о том, кто подписался по ссылке. Это не доказывает состояние возможного экземпляра на другом сервере.

## Фактически подтверждено

- Реальный amoCRM GET вернул сделку `32426619`, `pipeline_id=11037010`, `status_id=143`. Группа определяется по pipeline_id, поэтому здесь это действующие — сам status_id=143 не заменяет правило воронки.
- До проверки в сделке было 16 примечаний и не было примечания подписки бота.
- Реальный POST создал **техническое проверочное примечание `359106103`** в сделке `32426619`. GET подтвердил entity_id и текст. PATCH того же ID выполнен, повторный GET подтвердил обновлённый текст. В списке сделки найдено ровно одно примечание с маркером технической проверки. Оно явно обозначает проверку API, а не подписку клиента.
- Telegram getMe подтвердил `sinai_news_bot`; webhook отсутствует. MAX `/me` и `/subscriptions` ответили успешно, подписок webhook нет.
- Приветствия реально доставлены через Telegram API администратору: сообщение `31` — точный текст и две inline-кнопки; сообщение `32` — тот же текст без inline-кнопок. Входящие `/start` для этих двух проверок поданы в штатный обработчик из тестового сценария; затем использована настоящая Telegram отправка из штатной очереди. Тестовая регистрация находилась во временной БД и не добавлена в рабочую БД подписчиков.
- Локальные тесты проверяют Telegram/MAX /start, повторный /start, deep link, повторную неуспешную привязку, единственного владельца сделки, POST/GET/PATCH примечания, обработчик CRM-очереди, HTTP 429, потерю ответа после принятого POST, восстановление отсутствующей задачи примечания, календарные даты и обновление следующей даты после отправки. CRM в этих автоматизированных сценариях имитируется через httpx.MockTransport; они не выдаются за реальные клиентские подписки.
- Последний запуск: **12 тестов прошли**.
- Реальный локальный процесс стартовал, выполнил задачу синхронизации CRM (`sync=done`) и успешный polling Telegram (`poll_ok:tg`). Затем Telegram вернул **HTTP 409**, подтверждающий конкурирующий polling-экземпляр с тем же токеном. Локальный процесс сам остановился. Проверка состояния очереди и журнал находятся в `data/sinai.sqlite3` и `data/bot.stderr.log`.

## Что пока не подтверждено

Реальный ID пользователя, подписавшегося по ссылке `32426619`, отсутствует в локальных данных и ожидающих обновлениях Telegram. Поэтому **клиентская подписка и её персональное примечание в этой сделке пока не подтверждены**. Нельзя привязать администратора или вымышленного пользователя вместо клиента. Нужен реальный ID подписавшегося либо новый реальный переход по ссылке при работающем экземпляре исправленного бота.

Примечание подтверждено в API-списке и по ID сущности; визуальная проверка открытой карточки в браузере не выполнялась. Исправленный код необходимо запустить/перезапустить в том экземпляре, который принимает polling этих токенов; сам факт редактирования файлов не обновляет другой сервер. Повторный локальный экземпляр не оставлен работающим. Чтобы завершить реальную проверку клиентской подписки, нужны место запуска действующего экземпляра и ID клиента (либо новое событие /start от него).
