# Синай · Telegram + MAX + amoCRM

Python 3.12+, один процесс, SQLite WAL, исключительно long polling. Имеющийся `.env` используется без изменения. Новые сделки и контакты не создаются; бот пишет только примечание подписки в существующую сделку. Состояние CRM всегда имеет преимущество над выбором пользователя: воронка `8993570` → завершённые, любая другая → действующие. Бот не изменяет воронки и этапы CRM.

## Запуск

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m sinai
```

Для Linux: `python3.12 -m venv .venv`, `.venv/bin/pip install -r requirements.txt`, `.venv/bin/python -m sinai`. Запускайте из корня проекта. Параметры и дополнительные настройки перечислены в `.env.example`. Для обновления зависимостей меняйте закреплённые версии осознанно. В репозиторий не должны попадать `.env`, БД и медиа.

Бот на старте проверяет личности ботов и отсутствие webhook. Найденные webhook он самостоятельно не удаляет; перед polling удалите прежние подписки через настройки предыдущей интеграции/API. Не запускайте два процесса с одними токенами. Файловая блокировка запрещает повторный запуск на той же локальной БД; между серверами ответственность за единственный экземпляр у оператора.

## Linux / systemd

Разместите проект в `/opt/sinai-crm-bot`, создайте системного пользователя `sinai`, виртуальное окружение и каталог `data`. `.env` должен принадлежать `sinai:sinai` и иметь права `600`, каталог `data` — `700`. Исходники должны быть доступны пользователю `sinai` для чтения. Не переносите Windows `.venv` на Linux, создайте её заново.

```bash
sudo useradd --system --home /opt/sinai-crm-bot --shell /usr/sbin/nologin sinai
sudo install -d -o sinai -g sinai -m 700 /opt/sinai-crm-bot/data
sudo chown sinai:sinai /opt/sinai-crm-bot/.env
sudo chmod 600 /opt/sinai-crm-bot/.env
sudo cp /opt/sinai-crm-bot/deploy/sinai-bot.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now sinai-bot
sudo journalctl -u sinai-bot -f
```

При смене путей скорректируйте `WorkingDirectory`, `EnvironmentFile`, `ExecStart`, `ReadWritePaths`. Конфигурация systemd разрешает запись только внутри `data`. Для ручного запуска на Linux также используйте `umask 077`.

## Пользовательские сценарии

- `/start` — строго приветствие. Две кнопки групп показываются только до первого выбора; после выбора — только текст, без inline-кнопок и дополнительных уведомлений о регистрации. Повторный вызов сохраняет подписку и её дату.
- `https://t.me/sinai_news_bot?start=32376521` и `https://max.ru/<имя_бота>?start=32376521` — привязка после выбора группы. Первым владельцем становится пользователь, первым выбравший группу. Резервирование атомарное, одно на сделку для обеих платформ. Прямой числовой lead ID является доверенной ссылкой приглашения, а не доказательством личности; распространяйте такие ссылки адресно.
- Без lead ID запрашивается собственный контакт. В Telegram проверяется `contact.user_id`, в MAX — HMAC-SHA256 по документированному `vcf_info`, с постоянным временем сравнения. Пересланные неподтверждённые контакты отвергаются.
- Поиск amoCRM пагинируется; результат fuzzy query дополнительно проверяется по нормализованному PHONE. Только один точный контакт с единственной связанной сделкой допускает автоматическую привязку. При отсутствии/неоднозначности подписка остаётся действующей.
- `/status` — состояние подписки, `/stop` — приостановка, `/start` — возобновление.

## Администрирование

`/admin` разрешён только `ADMIN_ID` в Telegram и `MAX_ADMIN_ID` в MAX, только в личных диалогах. Панель показывает подписчиков, платформы, группы, привязки, включённые рассылки, активность за 30 дней и состояния доставки.

«Несинхронизированные» содержит пагинацию и карточки. «Привязать по ID пользователя» принимает `tg 123456789` или `max 123456789`, затем lead ID. Сделка проверяется в фоновой очереди. Конфликт владельца отклоняется, существующая связь не заменяется. Ошибки CRM сохраняются в очереди для повторной попытки; подписка не исчезает. Интервал завершённых — 1 или 2 календарных месяца, сохраняется в SQLite.

`/message` → аудитория → HTML-текст и вложения → предпросмотр → подтверждение. Поддерживаются действующие, завершённые, все, несинхронизированные. Текстовое сообщение заменяет общий текст, фото/видео/документ добавляется к черновику со своей подписью. `/clear` очищает черновик. Общая разметка: `b`, `strong`, `i`, `em`, `u`, `s`, `strike`, `a href="https://…"`, `code`, `pre`. Передавайте теги буквальным текстом. До 3900 символов без вложений, до 1000 с вложениями, до 10 вложений. Отличающиеся общий текст и подпись не теряются: общий текст идёт отдельным сообщением, затем вложения.

Предпросмотр приходит обоим указанным администраторам, поэтому до первого предпросмотра **обязательно запустите оба бота с соответствующих администраторских аккаунтов**. Подтверждение разрешается после доставки всех частей предпросмотра обеим платформам. Старое подтверждение после изменения черновика не действует. Подтверждённые рассылки нельзя редактировать. В «Прогресс» учитываются части сообщений, а не число людей; каждое вложение отправляется отдельным сообщением.

Медиа скачивается в `data/media`, загружается в MAX и затем переиспользуется; file_id Telegram и токен MAX сохраняются. Лимит проекта по умолчанию — **20 МБ** для совместимости с облачным `getFile` Telegram; фотографии для Telegram должны соответствовать его ограничениям (в частности, до 10 МБ). API платформы может отклонить неподходящий формат. Такие ошибки видны в очереди. CDN-адреса проверяются, произвольные URL не скачиваются, TLS-проверка не отключается. Если MAX требует дополнительный доверенный CA, укажите PEM bundle через `TLS_CA_BUNDLE`.

## Надёжность и границы гарантий

Долгие операции идут через сохранённые в SQLite очереди: входящие события, интерфейс, CRM, медиа, формирование получателей, доставка. Cursor/marker и входящие события записываются одной транзакцией до подтверждения платформе. Уникальные ключи исключают повторную обработку события, повторное подтверждение кампании и повторную локальную отправку за календарный период. Лимиты: 5 запросов/с amoCRM, до 20 запросов/с каждому боту, отдельное ограничение на диалог. HTTP 429, явное `attachment.not.ready`, ошибки соединения до отправки запроса повторяются с exponential backoff. Заблокировавшие бот пользователи отключаются от рассылок.

Периоды считаются от первоначальной даты подписки в `TIMEZONE`, календарными месяцами, с корректным последним днём короткого месяца. Просроченные периоды не отправляются пачкой: выполняется только актуальный период. Группа/интервал повторно проверяются непосредственно перед отправкой, при смене группы история периодов не сбрасывается. При запуске и периодически читаются воронки и все привязанные сделки. Для привязанных пользователей доставка ждёт актуальной проверки CRM; недоступность CRM не приводит к рассылке устаревшей группе.

**Exactly-once доставку внешний Bot API не гарантирует.** Если соединение оборвалось после отправки запроса или процесс остановился в момент отправки, сообщение могло быть принято платформой. Такая задача получает `unknown` и автоматически не повторяется: это предотвращает дубль, но может означать пропущенную доставку. Следующий календарный период продолжает работать. В панели неизвестные отправки выделены отдельно. Успех API означает принятие сообщения, а не прочтение пользователем. Кнопка повторения доступна только для явно неуспешных задач.

Примечание подписки содержит платформу, ID пользователя, точное время подписки, актуальную группу, следующую дату рассылки по календарному расписанию и периодичность. Сохраняются стабильные маркеры и ID примечания. Изменения обновляют то же примечание через PATCH; после POST/PATCH текст подтверждается GET. При запуске и периодической сверке восстановляются отсутствующие задачи привязки/примечания, а также перепроверяются примечания уже привязанных пользователей. Изменение интервала и результата автоматической отправки запускает обновление примечания через ту же очередь. При задержке доставки дата обозначает плановое время, фактическая отправка может задерживаться из-за ошибок API. После неопределённого результата POST идут только проверки появления маркера, без повторного создания. `request_id` amoCRM не трактуется как idempotency key.

Предоставленный access token может работать как долгоживущий. Автоматическое обновление OAuth доступно **только** с `AMOCRM_CLIENT_ID`, `AMOCRM_CLIENT_SECRET`, `AMOCRM_REFRESH_TOKEN`, `AMOCRM_REDIRECT_URI`; одного access token для refresh недостаточно. Новая пара сохраняется атомарно в защищённой БД. Если ответ сервера с новым refresh token потерялся, может понадобиться повторная OAuth-авторизация: нельзя восстановить использованный refresh token программно.

На дату реализации официальная документация MAX считает polling ограниченным по скорости/хранению событий и не рекомендует его для production. Здесь polling сохранён по требованию заказчика; продолжительный простой может приводить к потере событий, которые MAX уже не хранит. Также Telegram не хранит обновления бесконечно. Локальная очередь надёжно сохраняет только уже полученные события.

Резервное копирование работающей БД делайте через SQLite backup API (`sqlite3.Connection.backup`), а не копированием одного `.sqlite3` без WAL. Храните БД и медиа на локальном диске, не на сетевом файловом ресурсе. Журнал — stdout/systemd journal, без содержимого контактов и токенов. Таблица `audit` сохраняет административные изменения. Состояния poller и heartbeat доступны в `settings`; мониторинг процесса и ошибок journal настройте на сервере. Долгосрочную архивацию/удаление истории очереди и медиа планирует оператор; ключи автоматических отправок нельзя удалять до окончания соответствующих периодов.

Для точечного исправления `/start` и примечаний добавлены `tests/test_subscription_fixes.py`. Запуск: `.venv/Scripts/python -m pytest -q tests/test_subscription_fixes.py` (на Linux — `.venv/bin/python`). Фактические проверки API и границы подтверждения перечислены в `FIX_VERIFICATION.md`.
